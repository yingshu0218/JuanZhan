# 档案库 V0.4 — 按依赖排序的 MVP 开发任务与验收路线

> 依据：`archive-prd-v0.4.md`（产品规则）、`archive-schema-v0.4.sql`（数据库）、`archive-openapi-v0.4.yaml`（档案库对外 API）、`converter-openapi-v0.4.yaml`（独立转换服务内部 API）。  
> 适用：使用 Codex 等编码助手逐项实施。任务编号是开发切片，不是自然日计划。**不要跳过依赖任务直接创建 UI 假数据并宣布完成**。

## 0. 开发边界与默认技术选择

- 单管理员/单实例；Python API（推荐 FastAPI）、SQLite + FTS5、前端 React 或 Vue 均可（选一种，不同时引入两套框架）；独立 Python Converter HTTP 服务；Docker Compose 两个主服务。
- 本地文件卷分为 managed（原件不可变）、derived（派生文件）、database、temporary（转换器任务临时产物）；external mount 必须宿主机 bind mount 且 `read_only=true`。
- SQLite 每连接 `PRAGMA foreign_keys=ON`；WAL；数据库写入短事务；禁止让转换器直接访问或修改档案库数据库。
- API 错误遵守 `Error` schema；UI 会话+CSRF / API Bearer Token；禁止无鉴权下载和预览。
- 文件 ID、来源 ID、版本 ID、解析 ID 均为不透明稳定 ID。哈希只是去重提示，绝不是 Document 主键。

## 2. 里程碑与验收闸门

### M0 · 能运行的服务与正确的数据（T01—T07）

- 档案服务及转换器能通过 Compose 启动；SQLite 迁移幂等；只读 API 受认证保护。
- 成功插入 Space/Folder/Document/Revision，非法跨空间 FK 或循环文件夹必须失败。
- 保存托管原件时崩溃，数据库不会引用不存在文件；worker 重启后任务不丢。

### M1 · 不依赖解析器的可用档案库（T08—T10、T17—T18、T26—T27）

- 上传 PDF、DOCX 或未知类型文件，都能作为原件成功归档。
- 收件箱、标签、逻辑目录、字段、回收站和基本批量动作可用。
- `document_version` 冲突、同哈希不同档案、必填字段校验有测试。

### M2 · 外部来源双模式（T11—T15、T28）

- 从只读 NAS 目录首次按树导入；之后新增文件入收件箱、旧文件逻辑目录不跟随变化。
- 断开挂载，不丢失已有档案和缓存；恢复挂载再扫描保持 document_id。
- 删除外部索引不影响源文件；恢复或移除排除规则可控。

### M3 · 可检索的内容资产（T19—T25、T29—T31）

- 六种主要格式能产生统一解析 JSON、块和 TXT/MD 内容；扫描件支持可选 OCR。
- 字段候选值人工采纳，解析失败继续展示旧成功正文并提示已过期。
- 中文、英文、短词、混合检索，以及 Decimal/日期筛选可自动验证。

### M4 · 可长期运行的交付（T32—T34）

- 安全文件处理、路径边界、HTML 防注入、备份和恢复通过测试。
- 30 条产品验收、关键 API 契约检查、SQLite 完整性、最小性能基线全部通过。
- 发布镜像、Compose 示例和迁移/备份文档齐全。

## 5. Codex 实施约定（建议写入 AGENTS.md）

1. **严格遵守现有五项规格**，新增接口先修 OpenAPI，字段变更先修 SQL migration 和 PRD，再写实现。
2. 每个任务独立提交：实现代码、数据库迁移（如需要）、API/Schema 更新、自动测试、README 操作方法。
3. 测试不能只用 Mock 验证自身，至少有一条真实 SQLite + 存储 + HTTP 的集成测试；涉及转换器的验收必须有实际样本文件。
4. 所有写入必须正确处理并发、失败与重试。若需要重跑 Job，不能产生第二条被误当“当前”的内容索引。
5. 不在界面展示来源绝对路径；文件和 HTML 均不可信；外部目录只读保证在 Docker 挂载级与应用级双重落实。
6. 不使用系统本地时间做业务主键；所有日期时间用 UTC，文档业务日期保留 `YYYY-MM-DD`。
7. 对任何暂未实现的能力明确 `501` 或隐藏控件，不能显示会误导用户成功的虚假操作。

### 开始开发建议

先让 Codex 实施 **T01 → T02 → T03/T04（可并行）→ T05 → T06 → T07**，并要求提交 SQLite FK/文件写入崩溃/认证三个基线测试；通过 M0 再推进页面和解析器。这样比直接从前端三栏界面开始开发更能控制返工。

## 6. 明确尚待编码阶段决策的事项

- 前端到底选 React 还是 Vue、后台 ORM 与迁移工具；要求选一种并在 T01/T02 固化。
- 具体中文分词实现：在 T24 用混合中英测试集比较“词项预处理 + FTS5”策略，记录 tokenizer_version，并设计不足两字短语回退。
- 解析器具体依赖与 OCR 资源包：在 T20/T21 用样本压测后选择；默认 OCR 关闭以降低轻量部署成本。
- 硬件性能与大规模目录基线：T34 先定义 1 万/10 万文档目标测试，不在未经实测前承诺吞吐量。
- 超大文件与扫描批次限制的具体默认值，需要通过 T08/T12 的资源测试确定，不能任意定成不合理常量。

**开发准入状态**：产品规则、SQL 初始迁移、公共 API 和任务拆分已有基线。MVP 尚未实现；上述文档与文件可直接作为首轮开发输入，但执行过程中应按测试反馈更新。
